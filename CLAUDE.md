Glass's own skills live in the `glass-skills` workspace at `crates/skillset/`, organized into bucket folders:

- `engineering/`: daily code work
- `productivity/`: daily non-code workflow tools
- `misc/`: kept around but rarely used, not promoted
- `in-progress/`: beta: public on purpose, feedback wanted, not shipped in the plugin
- `deprecated/`: no longer used

Every skill in `engineering/` or `productivity/` (the **promoted** buckets) must have a reference in the top-level `README.md` and an entry in `.claude-plugin/plugin.json`'s `skills` array (the Claude Code plugin ships exactly the promoted set). Skills in `misc/`, `in-progress/`, and `deprecated/` must not appear in either.

Install commands are copied verbatim from [.agents/install-block.md](./.agents/install-block.md). `.claude-plugin/marketplace.json` makes the repo its own single-plugin marketplace (a fallback the install block explains, not the documented route). Run `claude plugin validate . --strict` after touching either manifest. Why a Claude plugin but not (yet) a Codex one lives in [.agents/adr/0002-ship-as-a-claude-code-plugin.md](./.agents/adr/0002-ship-as-a-claude-code-plugin.md).

Each skill entry in the top-level `README.md` must link the skill name to its `SKILL.md`.

## Third-party skill suites

`crates/` holds the skill suites this plugin ships. `crates/skillset/` is glass's own (the `glass-skills` workspace). The other two are git submodules tracking `main` of their upstream repos, declared in `.gitmodules`; nothing under them is edited here. After cloning, or when `crates/gstack` or `crates/impeccable` is empty, run `git submodule update --init`. To upgrade, `git submodule update --remote crates/gstack crates/impeccable`, then `bun run agents`, re-sync the manifest, and commit the new gitlinks. CI checks out with `submodules: true`.

Known cost: Claude Code plugin installs and the Devin plugin loader fetch the repository without submodules, so an installed plugin only sees the submodule content when its installer resolves submodules. Devin also reads a `triggers` key in `SKILL.md` frontmatter as the skill's invocation policy (it expects `model` and `user`), and upstream gstack skills carry a `triggers` list of example phrases, so Devin hides them. Both were accepted when the vendored copies were replaced by submodules; if either bites, the fix is upstream or a generated copy, never an edit inside a submodule.

### gstack

[garrytan/gstack](https://github.com/garrytan/gstack) is the submodule at `crates/gstack`. `.claude-plugin/plugin.json` lists `./crates/gstack` (its router skill) and every `./crates/gstack/<name>` directory that holds a `SKILL.md` (not the `connect-chrome` symlink alias), and `bun run check` requires that list to match the tree exactly.

`agents/*.md` are subagent profiles generated by `scripts/agents.ts` and listed in `plugin.json`'s `agents` array. From `crates/gstack/review/specialists/*.md` it renders one `<name>-reviewer` per checklist (the description map lives in the script; the checklist text is gstack's verbatim, so the no-em-dash rule below does not apply to those copied sections). Never edit the generated files by hand: change the script or update the submodule, then run `bun run agents`. `bun run check` fails when they are stale.

Every agent profile must load in both Claude Code and Devin, whose [custom subagent format](https://docs.devinenterprise.com/cli/subagents#custom-subagents) is the stricter one: frontmatter holds only `name`, `description`, and `tools` as a YAML list (no `model`, `effort`, or `maxTurns`). `bun run check` enforces this.

gstack skills are not linked into `.devin/skills`, are not routed by `ask-matt` (gstack ships its own `/gstack` router), and get no docs page. Their `SKILL.md` files expect gstack's `./setup` to have installed `~/.claude/skills/gstack/bin`; without it they run in gstack's documented degraded mode.

### impeccable

[pbakaus/impeccable](https://github.com/pbakaus/impeccable) is the submodule at `crates/impeccable`. It ships a real Claude plugin under `plugin/`, and the manifest points straight into it for the skill: `./crates/impeccable/plugin/skills/impeccable`. Its four agents under `crates/impeccable/plugin/agents/*.md` carry `model`, `effort`, `maxTurns`, and a comma-separated `tools` string, which Devin rejects, so `scripts/agents.ts` writes a trimmed copy of each into `agents/` (same filename, frontmatter reduced to the shared format above) and the manifest lists those copies. Upstream's `hooks/hooks.json` and nested `.claude-plugin/` are not shipped. Always point at upstream `plugin/`, never `.claude/` (that copy hard-codes `.claude/skills/impeccable/scripts` paths).

Each bucket folder has a `README.md` that lists every skill in the bucket with a one-line description, with the skill name linked to its `SKILL.md`. The promoted buckets' `README.md`s and the top-level `README.md` list skills under **Model-invoked**; non-promoted bucket `README.md`s (`misc/`, `in-progress/`) use a flat list.

Skills in `engineering/` and `productivity/` also have a human-facing docs page at `docs/<bucket>/<skill-name>.md` (the docs tree mirrors those two bucket folders under `crates/skillset/`). The published URL is `https://aihero.dev/skills-<skill-name>` regardless of bucket: the docs path is repo organisation only. When you add, rename, or change the behaviour of a skill in `engineering/` or `productivity/`, create or re-sync its docs page following [.agents/writing-docs.md](./.agents/writing-docs.md). A finished page carries four sections: **What it does**, **When to reach for it**, **Common questions**, and **It's working if**. `writing-docs.md` holds the template, the section order, and where to hunt for the questions. Skills in the non-promoted buckets (`misc/`, `in-progress/`, `deprecated/`) get **no** docs page. The one exception is a promoted skill removed outright: its page stays, marked archived (see `writing-docs.md`).

Every `SKILL.md` is model-invoked and user-reachable. Keep descriptions trigger-focused and omit user-only restrictions from frontmatter and `agents/openai.yaml`. See [.agents/invocation.md](./.agents/invocation.md).

[`ask-matt`](./crates/skillset/engineering/ask-matt/SKILL.md) is the router that maps every user-reachable skill and how they relate. The same trigger that re-syncs a docs page applies to it: whenever you add, rename, remove, or change how a user-reachable skill fits the flows, re-read `ask-matt`'s `SKILL.md` and update it so the map stays accurate: a new skill it never mentions, or a stale one it still routes to, is a router that lies.

All buckets are available inside this checkout through relative symlinks in `.devin/skills`, with `.agents/skills` and `.claude/skills` pointing to that directory. After adding, removing, renaming, or moving a skill, run `bun run link-skills` and include the link changes with the source changes. `bun run check` validates links and invocation metadata. Edit sources under `crates/skillset/`, not installed plugin caches. The older `scripts/link-skills.sh` changes global installations; it is not the repository-local setup.

No em-dashes anywhere in this repo's prose (`SKILL.md` files, docs, `README.md`, `CHANGELOG.md`, ADRs, changesets, code comments). Where a sentence reaches for one, rewrite it instead with a comma, colon, period, parentheses, or a conjunction, whichever the sentence actually wants; never do a blind character substitution.

## Monorepo tooling

Use Bun for dependency installation and scripts. Run `bun run check` to verify formatting, lint, TypeScript, builds, tests, and promoted-skill manifest entries. Run `bun run check-plugin-version` separately before releasing.

The root package orchestrates workspaces. `crates/skillset/package.json` owns the plugin release version under the `glass-skills` package name so existing changesets still resolve. Release tooling lives in the private `@glass/scripts` workspace. New applications and libraries go under `apps/*` and `packages/*`; their TypeScript configs extend the root `tsconfig.json`.

Markdown files are importable. Bun's default `md` loader renders them to HTML, so add `with { type: "text" }` to get the raw Markdown string: `import readme from "../README.md" with { type: "text" };`. Either way the import is a `string`, typed by `types/markdown.d.ts`, which the root `tsconfig.json` includes for every workspace. See `scripts/markdown-import.test.ts`.
